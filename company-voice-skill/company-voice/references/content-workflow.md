# Content Workflow

Use this when planning, generating, reviewing, searching, backlogging, publishing, or reviewing performance.

## Context Selection

Before writing, inspect `.editorial-voice/00-index.md` and load only relevant files. Select files based on:

- topic
- target audience
- reader problem
- content purpose
- channel and format
- content pillar
- product, service, page, resource, or proof point
- technical depth
- claim risk
- CTA type
- search/discovery objective
- primary metric

Avoid loading old change history, unrelated pillars, every channel, every published post, or full performance logs unless required.

## Pre-Generation Plan

Create a short plan with:

- topic
- target audience
- reader problem
- purpose
- content pillar
- central idea
- organization perspective
- supporting evidence
- claims requiring verification
- technical depth
- tone
- format
- channel
- CTA type
- relevant product/service/page/resource
- primary success metric
- search phrase or discovery theme, where applicable
- loaded files

Ask for clarification only when a missing decision materially affects quality, accuracy, or risk.

## Generation Rules

- Follow stored editorial files over generic voice defaults.
- Use confirmed decisions first.
- Use provisional decisions only when relevant and label them in the plan or notes.
- Do not invent statistics, testimonials, clients, results, repositories, or case studies.
- Do not keyword-stuff.
- Do not repeat one structure mechanically across posts.
- Treat post structures as reasoning frameworks.
- Keep promotion within stored CTA and promotional-limit rules.
- Match technical depth to audience and channel.

## Review Checklist

Review against the smallest relevant subset of rules.

Blocking issues:

- factual inaccuracy
- unsupported claim
- invented statistic, testimonial, client, result, or case study
- contradiction with confirmed rules
- excessive promotion
- serious voice mismatch
- wrong audience or channel
- unclear or misleading CTA

Recommended improvements:

- stronger audience relevance
- clearer central idea
- better evidence framing
- less generic AI phrasing
- less repetition
- less jargon
- improved search alignment
- sharper reasoning

Optional stylistic changes:

- sentence rhythm
- stronger opening
- alternate CTA
- more or less humor, story, emotion, or data within allowed range

Fix blocking issues before presenting final content.

## Search And Discovery

Search visibility can be:

- `primary`
- `secondary`
- `irrelevant`

When search matters, support:

- topic discovery
- search-intent mapping
- primary search phrases
- supporting phrases
- topical clusters
- evergreen topics
- trend-based topics
- content-to-page mapping
- internal linking opportunities
- product and service relevance
- terminology consistency
- follow-up topics that strengthen topical authority

Use search phrases naturally. Never distort the stored voice for search optimization.

## Backlog Workflow

Keep backlog files separate from permanent editorial rules.

For each topic, record:

- ID
- title or working angle
- status
- audience
- pillar
- channel/format
- purpose
- priority
- primary metric
- search theme, if any
- related product/resource/page
- evidence required
- dependencies

Group related topics by pillar, search cluster, audience, product, or campaign.

## Publishing Workflow

When content is published, record in `content/publishing-log.md`:

- content ID
- title or topic
- channel
- format
- date
- linked files or decisions used
- CTA
- target metric
- URL or location, if available
- notes

Published content should not automatically become a permanent voice rule.

## Performance Review

Store performance observations in `metrics/performance-notes.md`.

When refining the editorial system from performance:

1. Separate signal from noise.
2. Identify which decision might change.
3. Decide whether the change is experimental or permanent.
4. Update only affected files.
5. Record the change.
6. Retire old decisions when needed.

Do not load performance history during normal content generation unless the user asks for it or it materially affects the task.
